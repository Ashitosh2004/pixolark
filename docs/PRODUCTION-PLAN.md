# Pixolark — Production Upgrade Plan (Master Spec Execution)

Working plan for executing the "Complete Production-Ready Messenger" master spec
on top of the existing codebase. Zero-database policy is absolute and unchanged.

## What already exists (kept, not rebuilt)

- E2EE 1:1 messaging over WebRTC DataChannels (`PeerSession.send`, AES-GCM-256,
  ECDH P-256 + HKDF, sequence-number replay protection) — `src/lib/pixel/crypto.ts`.
- Groups with owner/admin/mod/member roles, moderation, sender-key ratchet,
  host-relayed E2EE frames — `src/lib/pixel/group.ts`, `groupcrypto.ts`.
- Public room discovery via host beacons — `src/lib/pixel/discovery.ts` (kept as
  a live-direct source; superseded as the *primary* listing source by the signed
  static directory).
- 2,318 generated animated stickers (4,636 asset files, 24 packs) with
  versioned library + incoming-version guard — `scripts/build-stickers.ts`.
- Local encrypted IndexedDB (keys + history, opt-in, 24h auto-delete).
- Regional hierarchy (country → states → cities) and language catalogs.

## Locked-in architecture decisions

1. **Backend = Node.js + Express + WebSocket (`ws`).** No Socket.IO: the wire
   protocol stays plain JSON text frames, auditable, no vendor lock-in. Runs
   under Bun in dev (`bun server/src/index.ts`) and standard Node with a TS
   loader in production. **No database anywhere, no hidden persistence.**
2. **E2EE unchanged.** Every message still rides WebRTC DataChannels through
   `PeerSession.send`. The coordinator relays **only**: signed room manifests,
   presence, and WebRTC offer/answer SDP (public data by design, exactly like
   the existing ntfy topics). The server never sees message plaintext.
3. **Signed manifests = ECDSA P-256 over canonical JSON** (sorted keys, no
   whitespace, UTF-8). WebCrypto ECDSA works identically in browser, Bun, and
   Node ≥ 22. The owner's signing key is a *dedicated signing subkey*, distinct
   from the ECDH identity key; its public half is embedded in the manifest.
4. **Static room directory** = signed manifest files arranged
   global/countries/states/cities/categories/languages, generated by the owner
   tool and uploaded to ordinary HTTPS static hosting. The client verifies every
   manifest signature, enforces expiry, supports multiple mirrors, and caches.
   No server-side listing state.
5. **Coordinator availability is the truth.** A room is joinable only while its
   owner (or an authorized co-owner per manifest policy) holds a live lease on a
   coordinator. Otherwise Discover shows "Coordinator offline" / join shows
   "Room temporarily available"... **never faked.**
6. **ntfy stays as a manual/no-backend fallback transport** for signaling
   (QR/copy codes), because it is what makes zero-infrastructure P2P possible;
   the coordinator becomes the primary discovery + signaling path when one is
   configured. Beacons remain supported for backend-less discovery.
7. **MLS (RFC 9420):** blocked on a maintained, browser-runnable implementation.
   Research task in Phase 3; if none qualifies, the hardened sender-key ratchet
   stays and the deviation is documented honestly in SECURITY.md (no invented
   crypto).

## Phases

### Phase 1 — Foundations (server + manifests + directory tooling)
- `src/lib/pixel/manifest.ts`: RoomManifest schema, canonical JSON, ECDSA
  sign/verify, expiry/revocation, directory index types.
- `server/src/`: Express + ws coordinator. In-memory room registry verified
  against signed manifests, presence, WebRTC signaling relay, room leases,
  `GET /health`, stateless restart semantics (clients re-register; nothing is
  persisted; no fake online states).
- `tools/`: room manifest generator CLI + directory builder/publisher (static
  JSON tree, filesystem output + documented static-host adapters).
- Tests: sign/verify/tamper/expiry, directory integrity, coordinator
  register/lease/join/signal round-trip.

### Phase 2 — Client integration
- `src/lib/pixel/coordinator.ts`: WebSocket client with jittered exponential
  backoff, connection-state machine (connecting / reconnecting / restoring /
  verifying / rejoining / connected / room-unavailable / recovery-failed).
- Recovery registry in IndexedDB (encrypted): room manifests, joined-room
  references, last coordinator, drafts, prefs; password-protected export /
  import / device transfer / clear.
- Discover reworked: directory listings (signature-verified) merged with live
  coordinator status and beacon listings; honest offline states.
- Owner-based recovery: re-register on coordinator restart; co-owner takeover
  only when the manifest policy authorizes it.

### Phase 3 — Protocol + catalogs + docs
- Message synchronization (IDs, sequence gaps, duplicate suppression, recovery
  requests from surviving encrypted copies).
- MLS research + decision (or documented deviation).
- Region catalog extended to country/state/city (Kolhapur, Belgaum, Mumbai,
  Pune, Bengaluru...), language directories. ✅ 2026-11-21 — `REGIONS` now ships
  per-state city lists; the create wizard, beacons, Discover filters and signed
  manifests all carry `region`/`subRegion`/`city` end-to-end.
- Sticker packs extended to the full 20-category list. ✅ 2026-11-21 — food,
  greetings, celebration, india, nature, space, sports, music, travel and study
  packs generated via `stickers:build`; the library is now 1,934 stickers
  (3,868 asset files), version-guarded as before.
- Sticker library extended beyond the original 20. ✅ 2026-11-21 — work, money,
  tech and pets packs (12 concepts × 8 characters each) added via the same
  pipeline; the library is now 2,318 stickers (4,636 asset files),
  version `pxs1-91930c1c3cc8`.
- README, `.env.example`, `start.bat`, DEPLOYMENT/TESTING/SECURITY/RECOVERY docs.

## Honesty rules (from the spec, enforced)

- Never fake online counts, availability, or recovery; missing data says so.
- Public-room encryption is described truthfully: members can read what they
  receive; the room is not private *from its members*.
- If every encrypted copy of a message is gone, say "cannot be recovered".
